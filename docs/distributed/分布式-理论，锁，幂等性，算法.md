# 分布式与集群

## 分布式与集群的区别

- 分布式： 一个业务分拆多个子业务，部署在不同的服务器上
- 集群：同一个业务，部署在多个服务器上

## 分布式和集群有什么区别

- 两个是不同的概念，尽管他们有一些相似之处，都用到了多台计算机协同工作。
- 分布式是多台计算机通过网络通信来处理一些复杂的任务。常用于大数据量和高并发的应用程序。
- 集群中多台计算机都运行一样的业务软件，处理相同的任务。常用于负载均衡，高可用性应用。
- 分布式关注的是任务的划分和协调，集群关注的是可用性和可扩展性。

## 分布式和微服务的区别

- 分布式： 一个业务分拆多个子业务，部署在不同的服务器上
- 微服务本身也是一种分布式的架构，不过微服务强调的是按功能去划分服务，强调业务解耦

## 什么是分布式（理解上的）

- 谈到分布式，就要讲一下传统架构-单体架构，所谓的单体架构，就是一个整体的服务都放置到一个服务器上。使用单体架构，单个服务器有性能贫瘠。
- 所以，就有了分布式架构，分布式架构把单体架构的整体服务拆分成多个服务，多个服务放置到不同的服务器上，这样就可以使用多个服务器上的性能了，可以处理更多的数据。

## 集群的无状态效果

- 在集群环境下，每个节点都是独立的，没有单独的状态。这意味着，当一个节点发生故障时，其他节点仍然可以继续工作，而不会受到影响。

## 分布式扩容：横向扩容，纵向扩容 分别是什么

- 纵向扩容：提高单个节点的处理能力，比如通过升级cpu、带宽、磁盘等方式
- 横向扩容：多加几个节点

# 分布式理论

## CAP

- 一致性、可用性、分区容忍性，CAP原则指定是，这三者只能满足两个。
- [CAP 定理的含义 - 阮一峰的网络日志 (ruanyifeng.com)](https://www.ruanyifeng.com/blog/2018/07/cap.html)
- 一致性：写操作后的所有读操作，都要返回写时候的值。
- 可用性：在集群中一部分节点失效了，集群整体还是能响应读写请求。
- 分区容忍性：分布式系统都分布在多个子网络中，每个子网络都是一个区，分区容错的意思，区间通信可能失败，但不会影响整个系统的使用。

## BASE:

- BASE 是 Basically Available（基本可用） 、 Soft-state（软状态） 和 Eventually Consistent（最终一致性） 三个短语的缩写。
- BASE理论是对CAP中的一致性和可用性进行一个权衡的结果,强调可用性。
- 理论的核心思想就是：
    - 基本可用和最终一致性。
    - 无法做到强一致，但每个应用都可以根据自身的业务特点，采用适当的方式来使系统达到最终一致性。

## Base 理论三要素

- 基本可用：基本使用是指分布式系统在出现不可预知的故障的情况下，允许损失部分可用性。但这不意味着系统不可用。
- 软状态：软状态指允许系统中的数据存在中间状态，并认为该中间状态的存在不会影响系统的整体可用性，即允许系统在不同节点的数据副本之间进行数据同步的过程存在延时。
- 最终一致性：强调的是系统中所有的数据副本，在经过一段时间的同步后，最终能够达到一个一致的状态。

## CAP的一致性和MySQl的ACID中的一致性有什么区别？

- 数据库一致性是指内部一致性
    - 比如转账，A向B转账，A-100，B+100 。事务前后A+B的金额是一样的。
- 分布式中的一致性，是指外部一致性
    - 比如分布式有A,B,C节点，那么我们像A写入数据hello，那么从节点B，C读取出来的数据也一定是hello

## 幂等性问题如何解决

一锁二判三更新
- 第一步先加分布式锁
- 第二步幂等性判断，可以基于状态机、流水表、唯一性索引来判断
- 三更新，如果判断通过直接更新进行持久化就行了


## 幂等性问题解决

- 幂等性：对于一个接口，无论调用了多少次，最终得到的结果都是一样的。
- 实现方式：
    - 前端拦截：按钮点一次后就设置为不可再点，但防君子不防小人
    - JVM锁：对于每一个请求之前加锁，然后去查询业务是否被执行过，如果执行过的话，就释放锁，返回方法。
        - 缺点：对于分布式系统，会失效
    - 分布式锁：首先获取分布式锁，如果获取不到锁，说明被执行过了，返回结果。
    - 数据库:
        - 给订单号设置为唯一索引
        - 悲观锁配合事务：
            - 先查询订单号的状态
            - 然后再执行操作
            - 最后更新订单号的状态字段
            - 把这三个操作放到一个事务
        - 乐观锁：update table_name set version=version+1 where version=0;



## 幂等性问题

- 幂等性：对于一个接口，无论调用了多少次，最终得到的结果都是一样的。
- 为什么需要幂等性
    - 分布式环境下，由于一个服务提供者提供的接口处理的比较慢，迟迟没有返回结果给服务调用者，服务调用者以为调用失败了，触发了重试机制。导致接口被重复调用，不符合我们的实际预期。
- 如何实现幂等性
    - 最常见的是使用我们的分布式锁
        - 处理服务的时候，获取分布式锁，如果获取不到，说明该服务正在处理，直接返回就行了。不做处理。


# 分布式锁

## Redis 实现的分布式锁

- 加锁：
    - 第一版：
        - setnx key value
        - 这种方式的缺点是容易产生死锁，因为客户端有可能忘记解锁，或者解锁失败。
    - 第二版：
        - setnx key value
        - expire key seconds
        - 给锁增加了过期时间，避免出现死锁。但这两个命令不是原子的，第二步可能会失败，依然无法避免死锁问题。
    - 第三版
        - 将加锁、过期命令编排到一起
        - set key value nx ex seconds
- 解锁：
    - del key
- 问题：进程A在任务没有执行完毕时，锁已经到期被释放了。等进程A的任务执行结束后，它依然会尝试释放锁，因为它的代码逻辑就是任务结束后释放锁。但是，它的锁早已自动释放过了，它此时释放的可能是其他线程的锁。

## Redis实现分布式锁

- 简单的实现：
    - 加锁：setnx key value
    - 解锁：del key
    - 问题：带来死锁
    - 解决办法：添加过期时间
- 过期时间的实现
    - 加锁：setnx key value
    - 设置过期时间：expire key 秒数
    - 解锁：del key
    - 问题：不是原子性
    - 解决办法：redis 支持加锁和设置过期时间编排成一条
- 加锁和设置过期时间编排成一条原子性命令：
    - 加锁并设置过期时间：set key value ex 秒数 nx
    - 解锁：del key
    - 问题：del key 可能删除的是别人的锁，因为我的锁可能过期自己释放了
    - 解决办法：为value 设置一个uuid作为唯一标识，解锁时候判断是不是自己的uuid，是再删除
- 为value设置一个uuid
    - 解锁的过程：先获取key的value值是自己的uuid，如果是，再删除掉
    - 问题：判断是不是自己的uuid和删除key的命令不是原子性的
    - 解决：引入lua脚本，因为lua脚本是原子性的
    - 问题：过期时间还是不好评估
- Redisson框架
    - 引入Redisson 框架，内部有一个看门狗机制，看门狗机制就是一个守护线程，它会对锁自动续期来避免锁的过期

## 本地锁和分布式锁的区别

- 本地锁的意义
    - 单系统架构中，存在多个线程同时修改某个变量的值的时候，就需要对变量做同步控制，使其在多线程环境执行能够达到预期。
- 分布式锁的意义
    - java提供的锁只能作用在单个JVM，对于分布式系统，不同模块分布在不同的JVM中，本地锁就没有意义。所以就需要分布式锁来解决问题。
    - 常见的分布式锁：
        - 基于数据库实现
            - 数据库中创建一张表，字段上加上唯一索引，想要执行某个方法，就使用这个方法名插入表中，如果插入成功，表示获得锁，执行完成后删除相应的记录。
        - 基于Redis实现
            - setnx lock true 返回1说明成功获得锁，执行完后 del key 释放锁
            - expire命令为锁添加一个超时时间
                - 如：expire lock 30
            - setnx lock true 和 expire lock 30 不是原子性操作，所以有可能前者成功了，后者设置过期时间失败了，可以使用set lock true ex 30 nx
        - 基于Zookeeper实现

# zk实现分布式锁

在分布式系统中，ZooKeeper 是一个常用的工具，用于实现分布式锁。ZooKeeper 通过其独特的节点（ZNode）和数据模型来提供分布式协调服务。以下是用 ZooKeeper 实现分布式锁的基本步骤：
1. **创建锁节点**：当客户端需要获取锁时，它会在 ZooKeeper 中创建一个临时序列节点（ephemeral sequential node）。这个节点通常在锁的父节点下创建。
2. **获取锁节点列表**：创建节点后，客户端会获取锁父节点下的所有子节点，并对它们进行排序。客户端检查自己创建的节点是否是列表中的第一个节点。
3. **检查锁状态**：如果客户端创建的节点是列表中的第一个节点，则它获得锁。否则，它会监视排在自己前面的节点（列表中的前一个节点）。
4. **等待锁释放**：如果客户端没有获得锁，它将等待它监视的节点被删除。这通常发生在锁的持有者释放锁并删除其锁节点时。
5. **获取锁**：一旦客户端发现它监视的节点被删除，它会再次检查自己是否是列表中的第一个节点。如果是，它就获得锁。
6. **释放锁**：当客户端完成操作后，它需要释放锁。这通常通过删除它之前创建的临时节点来完成。
ZooKeeper 分布式锁的优点是它简单且易于理解。然而，它也有一些缺点，如性能问题（特别是在写操作频繁的情况下）和网络问题（如果 ZooKeeper 集群中的机器发生故障）。
在实施时，开发者需要考虑系统的具体需求和环境，以确保选择最适合的分布式锁方案。

## redis实现分布式锁和zk实现分布式锁，哪一个更好

- redis集群是属于cap理论的ap模型，即使有RedLock算法（过半同步机制算成功），也没法保证100%可靠。

- redis 实现分布式锁大部分场景都不会遇到极端的情况，其实也能胜任的。不过属于cp模型的zk更推荐。

## 一致性哈希算法

[https://www.bilibili.com/video/BV1Hs411j73w](https://www.bilibili.com/video/BV1Hs411j73w) 这个7分钟的视频一看就懂
- 为什么需要（hash算法在分布式环境的缺点）？
	- 传统的hash算法在分布式环境下具有的缺陷：比如对于redis cluster模式，有一天我们突然新增一个节点，hash算法 hash(key)%n 。 因为n变成 n+1，我们根据原有的算法就查找不到数据具体在哪一个节点上了。
	- 要解决这个问题的办法，就需要我们进行**迁移数据**，重新对数据和节点做映射。但是成本太高了，所以需要一个更好的算法来避免对于扩容缩容的场景下出现的这个问题。
- 哈希算法是对节点的数量进行取模运算，而**一致哈希算法是对 2^32 进行取模运算，是一个固定的值**。
- 一致性哈希要进行两步哈希：
	- 第一步：对存储节点进行哈希计算，比如根据节点的 IP 地址进行哈希；
	- 第二步：当对数据进行存储或访问时，对数据进行哈希映射；
- 所以，**一致性哈希是指将「存储节点」和「数据」都映射到一个首尾相连的哈希环上**。
- **具体过程**：先把存储节点存储到环上。然后计算数据在环上的具体哪一个位置，然后把数据放到顺时针的下一个存储节点上。
