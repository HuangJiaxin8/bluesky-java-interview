# 对象问题

## 对象创建的主要流程

- 虚拟机遇到一条new指令时，先检查常量池是否已经加载相应的类，如果没有，必须先执行相应的类加载。
- 类加载通过后，接下来分配内存。
    - 若Java堆中内存是绝对规整的，使用“指针碰撞“方式分配内存；
        - 指针碰撞：如果Java堆的内存是规整，指针指示器向空闲的内存移动一段与对象大小相等的距离
    - 如果不是规整的，就从空闲列表中分配，叫做”空闲列表“方式。
        - 虚拟机维护一个列表来记录可用的内存，在分配的时候可以从列表中查询到足够大的内存分配给对象，接着更新列表记录。
    - 划分内存时还需要考虑一个问题-并发，也有两种方式:
        - CAS同步处理，
        - 本地线程分配缓冲(Thread Local Allocation Buffer, TLAB)。
- 然后内存空间初始化操作，接着是做一些必要的对象设置(元信息、哈希码…)，最后执行方法。

## 对象分配内存的并发安全问题

- 对象的创建是一个非常频繁的行为，可能会出现 正在给对象 A 分配内存，指针还没来得及修改，对象 B 又同时使用了原来的指针来分配内存 的情况。解决这个问题有两种方案：
    - 对分配内存空间的动作进行同步处理（采用 CAS + 失败重试来保障更新操作的原子性）；
    - 把内存分配的动作按照线程划分在不同的空间之中进行，即每个线程在 Java 堆中预先分配一小块内存，称为本地线程分配缓冲（Thread Local Allocation Buffer, TLAB）。哪个线程要分配内存，就在哪个线程的 TLAB 上分配。只有 TLAB 用完并分配新的 TLAB 时，才需要同步锁。通过-XX:+/-UserTLAB参数来设定虚拟机是否使用TLAB。

## 对象的访问定位

- Java程序需要通过 JVM 栈上的引用访问堆中的具体对象。对象的访问方式取决于 JVM 虚拟机的实现。目前主流的访问方式有 句柄 和 直接指针 两种方式。
    - 指针： 指向对象，代表一个对象在内存中的起始地址。
    - 句柄： 可以理解为指向指针的指针，维护着对象的指针。句柄不直接指向对象，而是指向对象的指针（句柄不发生变化，指向固定内存地址），再由对象的指针指向对象的真实内存地址。

## 直接指针

![](attachments/Pasted%20image%2020240202222052.png)

- 如果使用直接指针访问，引用 中存储的直接就是对象地址，那么Java堆对象内部的布局中就必须考虑如何放置访问类型数据的相关信息。
- 优势：速度更快，节省了一次指针定位的时间开销。由于对象的访问在Java中非 常频繁，因此这类开销积少成多后也是非常可观的执行成本。 HotSpot 中采用 的就是这种方式。

## 句柄

![](attachments/Pasted%20image%2020240202222045.png)

- Java堆中划分出一块内存来作为句柄池，引用中存储对象的句柄地址，而句柄中包含了对象实例数据与对象类型数据各自的具体地址信息
- 优势：引用中存储的是稳定的句柄地址，在对象被移动（垃圾收集时移动对象是非常普遍的行为）时只会改变句柄中的实例数据指针，而引用本身不需要修改。

## 什么是指针碰撞

- 一般情况下， JVM的对象都放在堆内存中（发生逃逸分析除外）。当JVM为新对象分配内存时，如果Java堆中内存是绝对规整的，所有被使用过的的内存都被放到一边，空闲的内存放到另外一边，中间放着一个指针作为分界点的指示器，所分配内存仅仅是把那个指针向空闲空间方向挪动一段与对象大小相等的实例，这种分配方式就是 指针碰撞。

## 什么是空闲列表

- 如果Java堆内存中的内存并不是规整的，不可以进行指针碰撞
- 虚拟机必须维护一个列表，记录哪些内存是可用的，在分配的时候从列表找到一块大的空间分配给对象实例，并更新列表上的记录，这种分配方式就是空闲列表。

## 什么是TLAB

- 把内存分配的动作按照线程划分在不同的空间之中进行，每个线程在Java堆中预先分配一小块内存,这就是TLAB

# 内存结构

## JVM的主要组成部分

![](attachments/Pasted%20image%2020240202222010.png)

- JVM包含两个子系统和两个组件：
    - 子系统：Class loader(类装载)，Execution engine(执行引擎)。
    - 两个组件：Runtime data area(运行时数据区)、 Native Interface(本地接口)
- Class loader(类装载)：根据给定的全限定名类名来装载class文件到运行时数据区中的方法区。
- Execution engine：字节码文件只是 JVM 的一套指令集规范，并不能直接交给底层操作系统去执行，因此需要特定的命令解析器执行引擎。
- Native Interface：与native libraries交互
- Runtime data area(运行时数据区域)：这就是我们常说的JVM的内存结构

## JVM内存结构（Java运行时数据区）

- 分为线程私有和线程共享
    - 线程私有的有：程序计数器，虚拟机栈，本地方法栈
    - 线程共享的有：堆，方法区
- 程序计数器：工作线程数量大于CPU内核数的时候，就会发生上下文切换，这时候就要一个计数器来记录当前线程的下一个字节码位置。
- 虚拟机栈：每次调用线程方法的时候都会创建一个栈帧，存放了线程方法的临时变量表，动态链接，操作数栈，方法返回值，返回地址等。调用方法时入栈，方法返回时出栈。
- 本地方法栈：跟虚拟机栈类似，只不过虚拟机栈是针对于java方法的，而本地方法栈是针对于native方法的。
- 堆：最大的内存空间，创建的对象都放到这里。分为年轻代，老年代，永久代（永久代JDK1.8改为元空间），其中年轻代又分为Eden区，Suvivor from和Suvivor to区。创建的小对象首先会放到Eden区，1次GC后会把存活的对象转移到S0区，再经过一次GC后转移到S1区，15次后还存活的对象会转移到老年区。内存不够会OOM
- 方法区：存放被虚拟机加载的类的元信息，如常量，静态变量和即时编译器编译后的代码。内部的运行时常量池存放编译后的常量。

## 虚拟机栈中的栈帧的内部结构

- 局部变量表：存放编译期的各种数据类型，对象引用
- 操作数栈：存放方法计算过程中产生的计算结果
- 动态链接：主要服务的是一个方法调用其他方法的场景。在java代码被编译为class文件时，所有变量和方法引用都作为符号引用保存在class文件里。在一个方法需要调用其他方法的时候，需要将类常量池中的方法符号引用改为方法的直接引用（实际地址）。
- 方法返回地址

## 关于栈OOM的问题

- 在有些虚拟机中，栈是可以动态扩容的，比如早期的classic，如果无法申请到内存，那么就会抛出OOM异常。
- 有些虚拟机的栈是无法动态扩容的，比如Hotspot，那么不会抛出OOM，只会抛出SOF.

## JMM（Java内存模型）

- 规范：JMM 是和多线程相关的一组规范，需要各个 JVM 的实现来遵守 JMM 规范，以便于开发者可以利用这些规范，更方便地开发多线程程序。
- 作用：JMM屏蔽掉各种硬件和操作系统的内存访问差异，以实现让java程序在各种平台下都能达到一致的并发效果。
- 定义：Java内存模型规定**所有的变量都存储在主内存**中，包括实例变量，静态变量，但是不包括局部变量和方法参数。每个线程都有自己的工作内存，**线程的工作内存保存了该线程用到的变量和主内存的副本拷贝，线程对变量的操作都在工作内存中进行**。**线程不能直接读写主内存中的变量**。

## JMM定义了什么？

- JMM围绕着三个特征建立起来的 , 分别是：原子性，可见性，有序性。这三个特征可谓是整个Java并发的基础。

## JVM中的常量池

- Class文件常量池：编译的时候，就把.java文件编译成.class文件存放到磁盘，.class文件包括class文件常量池。
- 运行时常量池：运行时常量池是方法区的一部分。Class文件中除了有类的版本、字段、方法、接口等描述信息外，还有一项信息是常量池表（Constant Pool Table），用于存放编译期生成的各种字面量与符号引用，这部分内容将在类加载后存放到方法区的运行时常量池中。
- 字符串常量池

## 方法区

- 概念：存储类信息的一块内存区域，是JVM的一块组成部分。
- 存储什么？
    - 类型信息（域信息，方法信息）
    - 静态变量
    - 运行时常量池
    - JIT热点代码
- 版本迭代的变化
    - JDK6以前，具体实现为永久代，静态变量存储在永久代
    - JDK7 永久代依然存在，但是字符串常量池和静态变量转移到堆中
    - JDK8 删除永久代，元空间代替。元空间使用的是直接内存，存储类型信息，常量，方法，字段。字符串常量池和静态变量依然在堆中。

## 为什么将永久代替换为元空间（深入理解Java虚拟机的内容）

- 如果动态加载的类比较多，容易产生OOM。虽然可以通过调参来设置永久代的大小，但是也不好管理。
- 而元空间使用的是直接内存，maxMetaspaceSize默认值为-1
- 有极少数方法（例如String::intern()）会因永久代的原因而导致不同虚拟机下有不同的表现。
- 想要从其他虚拟机移植优秀功能有困难，因为方法区实现上有差异，为了更好的发展，取消了永久代

## JDK7为什么将字符串常量池从永久代移到堆空间中

- 因为字符串常量池使用频率较高，像之前被放置在永久代中被回收的概率就比较低，导致永久代空间不够用，放在堆中，能够及时回收。

## 方法区可以实现垃圾回收吗

- 回收的主要是废弃常量和无用的类、
    - 无用的类的条件：
        - 堆不存在该类的实例
        - 加载该类的类加载器被回收了
        - 不存在该类对应的Class对象

JDK8中，字符串常量池不在元空间中，字符串常量池在JDK7中已经移到堆中，JDK8元空间存放的是字符串常量的引用

# 类加载相关

## 类的加载机制（类的生命周期和双亲委派机制吧）

Java类加载机制是Java运行时环境的一个重要组成部分，它负责在运行时找到和加载类文件。Java类加载机制主要包括以下几个步骤：
1. **加载（Loading）**：类加载器首先会通过类的全限定名来读取该类的字节码文件（.class文件），并将其转换成方法区的数据结构，同时在堆中生成一个对应的`Class`对象用于封装类在方法区内的数据结构。
2. **验证（Verification）**：验证阶段会检查加载的类是否符合Java虚拟机规范，包括类文件格式验证、元数据验证、字节码验证和符号引用验证。
3. **准备（Preparation）**：准备阶段为类变量分配内存，并设置默认初始值。这些变量所使用的内存都在方法区中进行分配。
4. **解析（Resolution）**：解析阶段将常量池中的符号引用替换为直接引用。这一阶段会把类、接口、字段和方法的符号引用转换为直接引用。
5. **初始化（Initialization）**：初始化阶段是类加载过程的最后一步，这个阶段会执行类的初始化代码，包括静态代码块和对静态变量的赋值。
Java类加载器主要有以下几种：
- **引导类加载器（Bootstrap ClassLoader）**：用于加载Java标准库中的类，这些类位于`<JAVA_HOME>/jre/lib`目录（或者由`-Xbootclasspath`参数指定）。
- **扩展类加载器（Extension ClassLoader）**：用于加载Java的扩展库，即`<JAVA_HOME>/lib/ext`目录或由系统属性`java.ext.dirs`指定的目录下的类库。
- **应用程序类加载器（Application ClassLoader）**：用于加载当前应用的类路径（Classpath）中的类库。
此外，用户还可以自定义类加载器来加载特定路径或网络的类。
类加载机制中的“双亲委派模型”是一个重要的概念，它要求除了顶层的引导类加载器外，其余的类加载器都应当有自己的父类加载器。类加载器在尝试自己加载类之前，首先委托给父类加载器进行加载，只有当父类加载器加载失败（即在它的搜索范围内没有找到所需的类）时，子类加载器才会尝试自己加载该类。
这种模型可以避免类的重复加载，同时在一定程度上也保证了Java程序的安全性。

## 类的生命周期

- 类的生命周期：加载、验证、准备、解析、初始化、使用和卸载。而验证、准备、解析又称为连接。
- 类加载过程：加载、验证、准备、解析、初始化
    - 加载：通过完成限定名去加载class文件，生成class对象
    - 验证：验证class的合法性，不会影响JVM安全
    - 准备: 为static变量分配内存，初始化值。
    - 解析：把符号引用改为直接引用
    - 初始化：是调用类的构造器过程


## Java 类什么时候加载

关键字：首次使用

在Java中，类被加载的时机并不是由类的申明决定的，而是由类的首次使用触发的。以下是一些常见的类加载时机：
1. **创建类的实例**：当使用`new`关键字创建一个类的实例时，如果该类还没有被加载到Java虚拟机中，那么类加载器会先加载这个类。
2. **访问类的静态变量或静态方法**：当访问一个类的静态变量或调用静态方法时，如果该类还没有被加载，则系统会首先加载这个类。
3. **使用反射**：当使用Java反射API对类进行反射调用时，如果该类还没有被加载，则会触发类的加载。
4. **初始化类的子类**：当初始化一个类的子类时，如果父类还没有被加载，则会先加载父类。
5. **运行时包含main方法的类**：当运行一个Java程序时，JVM会先加载包含`main`方法的类。
6. **动态语言支持**：当Java虚拟机启动时，如果指定了`-Xbootclasspath/a`参数，并且该参数指向的路径中有类文件，那么这些类也会被加载。
7. **使用`Class.forName()`**：当使用`Class.forName()`方法显式加载一个类时，如果该类还没有被加载，那么类加载器会加载这个类。
8. **接口中定义默认方法**：如果一个接口定义了默认方法，那么直接实现或间接实现该接口的类的初始化，可能会导致该接口被加载。
需要注意的是，类的加载、验证、准备、解析和初始化是类加载机制中的几个阶段，而上述提到的加载时机主要是指类的加载阶段。一旦一个类被加载到Java虚拟机中，它的初始化是延迟的，直到类的首次主动使用才会发生。主动使用包括前面提到的创建实例、访问静态变量或方法等。这种延迟初始化的策略可以提高程序的启动性能。

## 三种类加载器之间有继承关系吗？

关键字：没有，通过组合模式，每个类有parent属性维护了父类加载器

在Java中，三种类加载器——引导类加载器（Bootstrap ClassLoader）、扩展类加载器（Extension ClassLoader）和应用程序类加载器（Application ClassLoader）——之间存在一种层次关系，但并不是通过继承关系来实现的。相反，这种层次关系是通过组合（Composition）来实现的。
1. **引导类加载器（Bootstrap ClassLoader）**：这是Java虚拟机（JVM）的一部分，通常用原生代码（如C/C++）实现，负责加载Java标准库中的核心类。因为它不是Java代码实现的，所以没有对应的Java类。引导类加载器没有父类加载器。
2. **扩展类加载器（Extension ClassLoader）**：这个加载器是用Java实现的，是`sun.misc.Launcher$ExtClassLoader`类的实例。它负责加载`<JAVA_HOME>/lib/ext`目录中，或者由系统属性`java.ext.dirs`指定的目录下的类库。扩展类加载器的父类加载器是引导类加载器。
3. **应用程序类加载器（Application ClassLoader）**：这个加载器也是用Java实现的，是`sun.misc.Launcher$AppClassLoader`类的实例。它负责加载当前应用的类路径（Classpath）中的类库。应用程序类加载器的父类加载器是扩展类加载器。
在Java中，类加载器之间的关系通常是通过`ClassLoader`类的`parent`字段来维护的。每个类加载器都有一个父类加载器，除了引导类加载器。当类加载器需要加载一个类时，它会首先委托给它的父类加载器来尝试加载，如果父类加载器无法加载，它才会尝试自己加载。
这种层次关系确保了类加载器的委派模型，也就是著名的双亲委派模型，其中类加载器首先将加载请求委托给父类加载器，只有当父类加载器无法处理时，才由自己来加载。这种模型有助于避免类的重复加载，并提供了一种安全机制，确保Java核心API不会被恶意代码篡改。

##  类加载的过程是线程安全的吗

关键字：安全的，通过锁来实现

在Java中，类加载的过程是线程安全的。这是因为Java虚拟机（JVM）在加载类时，会确保只有一个类加载器和它的实例能够加载同一个类。这意味着，对于任何一个给定的类，其加载过程在全局范围内是同步的，即在任何时刻，只有一个线程能够加载该类。
这是通过类加载器的委派机制和类加载过程中的同步锁来实现的。当一个线程尝试加载一个类时，它会先检查该类是否已经被加载。如果尚未加载，类加载器会委托给其父类加载器进行加载。这个过程中，类加载器会使用同步机制来确保在多线程环境下，类的加载和初始化是安全的。
具体来说，类加载器在加载类时会使用锁来保护其内部数据结构，防止多个线程同时修改这些数据结构。此外，类的初始化过程中，JVM会持有一个锁，确保在类的初始化期间，其他线程无法初始化同一个类。这个锁通常被称为初始化锁（initialization lock）或类初始化锁（class initialization lock）。
因此，尽管类加载器可能会被多个线程并发使用，JVM的设计确保了类加载过程的线程安全性。这意味着，即使在多线程环境下，类加载器也能够正确地加载和初始化类，而不会出现数据竞争或状态不一致的问题。

# GC相关

## java中的四种引用

- 强引用：发生gc不会被回收
- 软引用：内存溢出的时候才会被gc回收
- 弱引用：下一次gc的时候被回收
- 虚引用：用PhantomReference实现虚引用，虚引用的用途是在gc时候返回一个通知。

## Java 中 WeakReference 与 SoftReference 的区别？

- 虽然 WeakReference 与 SoftReference 都有利于提高 GC 和 内存的效率，但是 WeakReference ，一旦失去最后一个强引用，就会被 GC回收，而软引用虽然不能阻止被回收，但是可以延迟到 JVM 内存不足的时候。

## 如何判断对象可以被回收？

- 首先，垃圾回收器会去判断一个对象是否存活或者死亡，死亡的对象会被标记为等待清除。
- 而判断对象是否为死亡有两种算法：引用计数器算法和可达性分析算法
    - 引用计数器算法：创建对象的时候会设置一个计数器，对象被使用+1，使用完后-1，为0表示没有被使用，则标记为可清除。
        - 优点：实时性比较高，缺点就是无法解决循环引用的问题。
    - 可达性分析算法：
        - 指的是从对象的起点，即GC Roots开始向下搜索，如果对象到GC Roots没有任何引用链相连时，也就是说对象到GC Roots 不可达，表明此对象可以被回收。

## 垃圾回收算法有哪些

- 标记-清除算法：先标记需要清理的对象，所有都标记完后一次性清理掉
- 复制算法：将内存分为两块大小一样的空间，每次只使用一块，把一边还存活的对象移动另一边，然后清理掉这一边的空间
- 标记-整理：让存活的对象向一端移动，清掉端边界以外的空间
- 分代收集算法：把堆分为新生代和老年代，这样就可以根据各个年代的特点采用适合的垃圾收集算法

## 老年代和年轻代分别用什么算法？为什么

- 年轻代
    - 适合复制算法，也会发生stop the world
- 老年代
    - 标记-整理算法，不能使用复制算法，因为老年代需要放比较多的对象，不能使用复制算法浪费空间。而老年代gc的频率比年轻代gc频率低很多，使用标记整理算法比较合适。
    - 当然，也可以使用标记-清除算法（CMS），但是会产生过多的碎片。当碎片达到一定程度导致分配不了内存时，可以借助一些使用了标记整理的垃圾回收器整理一下内存空间(CMS 报错时候借助Serial Old )。

## 新生代细分

- 分为eden，survivor from ，survivor to区，默认比例是8:1:1

## 两种垃圾回收类型：Minor GC 和 Full GC

- Minor GC
    - 只对新生代进行回收，不会影响老年代。
    - 因为java对象在新生代死亡频繁，所以需要一种速度快的算法，使垃圾回收尽快完成。
- Full GC
    - Full GC 也叫Major GC，对整个堆进行回收。包括新生代，老年代和永久代。
    - 速度相对于Minor 更慢。
    - 导致Full GC的原因：
        - 老年代或永久代满了
        - System.gc()被显式调用

## Minor GC 和 Full GC的触发条件

- Minor GC触发条件：Eden区满了触发
- Full GC 触发条件：
    - 通过Minor GC进到到老年代，发现老年代内存不够
    - 老年代空间不足
    - 调用System.gc,系统建议Full GC，但是不一定执行

## Stop-the-World

- 运行垃圾回收的过程中，会涉及对象的移动。为了保证对象引用更新的正确性，必须暂停所有的用 户线程，像这样的停顿，虚拟机设计者形象描述为「Stop The World」。也简称为STW

## 安全点

- 程序执行时并非在任意位置都能够在停顿下来开始垃圾收集。必须到达特定位置，才能够执行GC。这个特定的位置就叫做安全点。
- 特点的位置有：
    - 循环的末尾
    - 方法返回前
    - 可能抛异常的位置

## 用代码能保证GC的执行吗？

- 不能，虽然可以调用System.gc()和Runtime.gc()，但是没办法保证GC的执行。

## GC Root

在Java中，垃圾收集器（GC）使用一系列称为“GC Roots”的对象作为起点来追踪和标记所有活动的对象。以下是可以作为GC Roots的对象类型：
1. 虚拟机栈（栈帧中的本地变量表）中的引用对象。
2. 方法区中的类静态属性引用的对象。
3. 方法区中的常量引用的对象。
4. 本地方法栈中JNI（即一般说的Native方法）的引用对象。
这些GC Roots是确定对象是否存活的一个基础集合，垃圾收集器会从这些根对象开始，递归地标记所有可达的对象。如果一个对象不能从任何GC Root通过引用链到达，那么它被认为是不可达的，即可以被垃圾收集器回收。

## 三色标记算法

- JVM中的**CMS、G1垃圾回收器**所使用垃圾回收算法即为三色标记法。
- 三色标记法将对象的颜色分为了黑、灰、白，三种颜色。
    - **白色**：该对象没有被标记过。（垃圾对象）
    - **灰色**：该对象已经被标记过了，但该对象下的属性没有全被标记完。（GC需要从此对象中去寻找垃圾）
    - **黑色**：该对象已经被标记过了，且该对象下的属性也全部都被标记过了。（程序所需要的对象）
- 流程：
    - 首先创建三个集合：白、灰、黑
    - 将所有对象放入白色集合中
    - 然后从根节点开始遍历所有对象，把遍历到的对象从白色集合放入灰色集合
    - 之后遍历灰色集合，将灰色对象引用的对象从白色集合放入灰色集合，之后将此灰色对象放入黑色集合
    - 通过write-barrier检测对象有变化
    - 清除所有白色对象

## 三色标记存在的问题


- 浮动垃圾
    - 并发标记的过程中，若一个已经被标记成黑色或者灰色的对象，突然变成了垃圾，由于不会再对黑色标记过的对象重新扫描,所以不会被发现，所以成为了浮动垃圾，浮动垃圾对系统的影响不大，留给下一次GC进行处理即可
- 对象漏标问题
    - 并发标记的过程中，一个业务线程将一个未被扫描过的白色对象断开引用成为垃圾（删除引用），同时黑色对象引用了该对象（增加引用）（这两部可以不分先后顺序）；因为黑色对象的含义为其属性都已经被标记过了，重新标记也不会从黑色对象中去找，导致该对象被程序所需要，却又要被GC回收，此问题会导致系统出现问题
    - 而CMS与G1，两种回收器在使用三色标记法时，都采取了一些措施来应对这些问题，CMS对增加引用环节进行处理（Increment Update），G1则对删除引用环节进行处理(SATB)

## 生代垃圾回收器和老生代垃圾回收器都有哪些？有什么区别？


- 新生代回收器：Serial（单线程）、ParNew（多线程）、Parallel Scavenge（多线程，可控制吞吐量）
- 老年代回收器：Serial Old（单线程）、Parallel Old（多线程）、CMS（多线程，牺牲吞吐量提高短停顿时间）
- 整堆回收器：G1
- 新生代垃圾回收器一般采用的是复制算法，复制算法的优点是效率高，缺点是内存利用率低；老年代回收器一般采用的是标记-整理的算法进行垃圾回收。


## 3种新生代垃圾回收期有什么区别

Serial：单线程回收，会stf
Parallel New：可以看作是Serial的多线程版本，与serial相比，停顿时间会更短，适合多处理器
Parallel Scavenge：也是多线程处理，但是它关注的是吞吐量，可以通过调参控制吞吐量或者停顿时间，适用于后台运算而不需要太多交互的任务

## 详细介绍一下 CMS 垃圾回收器？

- CMS 是英文的全程是 Concurrent Mark-Sweep ，它以牺牲吞吐量为代价来获得最短回收停顿时间。
- CMS 使用的是标记-清除的算法实现的，所以在 gc 后会产生大量的内存碎片，当碎片过多的时候导致无法分配内存，系统将会出现Concurrent Mode Failure（并发失败），这时会借助 使用标记-整理算法的Serial Old 回收器进行垃圾清除。
- 分为四个步骤，包括：
    - 初始标记（CMS initial mark） 会STF 
	    - 这个阶段会暂停所有的用户线程（Stop-The-World），标记出所有从GC Roots可达的对象。
    - 并发标记（CMS concurrent mark）
	    - 在这个阶段，CMS收集器与用户线程并发运行，它会遍历从初始标记阶段找到的存活对象，并标记出这些对象的引用。
    - 重新标记（CMS remark） 会STF
	    - 这个阶段会再次暂停所有的用户线程，用于处理在并发标记阶段由于用户线程运行而导致的对象状态变更。
    - 并发清除（CMS concurrent sweep）
	    - 在这个阶段，CMS收集器会清除未被标记的对象，并且这个阶段是与用户线程并发执行的。
- 缺点：
    - 1.多碎片
    - 2.多线程，短停顿时间
    - 3.会并发失败（Concurrent Mode Failure），导致full gc，借助标记整理算法的垃圾处理器Serial Old来清理
    - 浮动垃圾：由于CMS收集器在清除阶段是与用户线程并发执行的，因此可能会产生“浮动垃圾”，即有些垃圾可能在本次垃圾回收过程中未被清除，需要等到下一次垃圾回收时才能清除。

## G1收集器

- G1全名叫：Garbage first
- G1收集器开创了收集器 面向局部收集 的设计思路和基于Region的内存布局形式 
- 在G1收集器出现之前的所有其他收集器,垃圾收集的目标范围要么是整个新生代,要么就是整个老年代,再要么就是整个Java堆。而G1跳出了这个限制,它可以面向堆内存任何部分来组成回收集进行回收,衡量标准不再是它属于哪个分代,而是哪块内存中存放的垃圾数量最多,回收收益最大,这就是G1收集器的Mixed GC模式。

## G1 收集器

- G1全名叫：Garbage first
- G1收集器开创了收集器 面向局部收集 的设计思路和基于Region的内存布局形式
- 传统收集器都是按分代的理论，把堆分成年轻代，老年代。而G1不走寻常路，它把堆分成大小一样的Region区域。Region区可以在回收过程中可以根据需要扮演年轻代老年代的角色。
- G1收集器的局部收集思想主要是指它只回收垃圾比较多的Region区，所以效益是比较高的，这也叫做Mixed GC模式。
- 提供更可预测的垃圾回收暂停时间



## G1的垃圾回收过程包括以下几个阶段

初始标记（Initial Marking）：暂停所有用户线程，标记从GC Roots直接可达的对象。
并发标记（Concurrent Marking）：与应用程序线程并发执行，标记从GC Roots可达的对象。
最终标记（Final Marking）：暂停所有用户线程，处理剩余的SATB（Snapshot-At-The-Beginning）记录。
筛选回收（Live Data Counting and Evacuation）：暂停所有用户线程，选择回收价值最大的区域进行回收，这个阶段可能会进行多次，直到达到用户指定的停顿时间目标。



## G1有什么优缺点？


G1（Garbage-First）垃圾收集器是Java虚拟机（JVM）中的一个垃圾收集器，它旨在满足具有大内存需求的应用程序，并提供更可预测的垃圾收集暂停时间。
优点：
1. 低延迟：G1的主要设计目标是提供低延迟的垃圾收集，它通过将堆划分为多个区域（Region）并优先回收价值最大的区域来实现。这样可以减少全堆垃圾收集的频率，从而减少停顿时间。
2. 可预测的停顿时间：G1允许用户指定垃圾收集的最大暂停时间（如最多几百毫秒），它会尽力在这个时间限制内完成垃圾收集。
3. 整体上适用于多核机器：G1收集器可以充分利用多核CPU，提高垃圾收集的效率。
4. 空间整理：G1在回收内存时会进行压缩，减少内存碎片，这对于需要长时间运行的服务器应用程序来说尤其重要。
5. 可扩展性：G1适用于具有大内存需求的应用程序，可以管理数十GB甚至更多的堆内存。
缺点：
1. 内存占用：G1相比其他收集器可能会占用更多的内存用于额外的数据结构和维护信息，如Remembered Sets来跟踪跨区域的引用。
2. 性能开销：由于G1的复杂性和额外的内存占用，它在某些情况下可能会比其他收集器（如CMS）产生更高的性能开销。
3. 调优复杂性：G1提供了许多可调节的参数，这使得调优过程相对复杂。需要根据应用程序的特点和需求来进行细致的调优。
4. 年轻代收集开销：在某些情况下，G1的年轻代垃圾收集可能会比其他收集器（如Parallel GC）更昂贵。
5. 初始标记阶段的全局停顿：G1的初始标记阶段（Initial Mark）仍然需要一个全局停顿，虽然这个停顿通常很短，但在某些延迟敏感的应用程序中可能会产生影响。
总的来说，G1垃圾收集器适合需要低延迟和大内存管理的应用程序，但它可能需要更多的内存和更复杂的调优。在选择垃圾收集器时，应该根据应用程序的具体需求和性能测试结果来做出决策。

## 小内存为什么不适合G1处理器

- G1的定位就是解决大内存的垃圾回收问题
- G1需要更多的内存开销：为了实现停顿时间更加精细化的管理，需要维护更多的数据结构
- G1有比较复杂的垃圾回收策略和较长的启动时间，如果小内存用G1处理器就优点大材小用了
	- 复杂的回收策略：初始标记、并发标记、最终标记、筛选回收



## 简述分代垃圾回收器是怎么工作的？

- 分代回收器有两个分区：老生代和新生代，新生代默认的空间占比总空间的 1/3，老生代的默认占比是 2/3。
- 新生代使用的是复制算法，新生代里有 3 个分区： Eden、 To Survivor、 From Survivor，它们的默认占比是 8:1 :1。它的执行流程如下：
    - 把 Eden + From Survivor 存活的对象放入 To Survivor 区；
    - 清空 Eden 和 From Survivor 分区；
    - From Survivor 和 To Survivor 分区交换， From Survivor 变 To Survivor， To  Survivor 变 From Survivor。
- 每次在 From Survivor 到 To Survivor 移动时都存活的对象，年龄就 + 1，当年龄到达 1 5（默认配置是 15，可以调小，15是最大值）时，升级为老生代。
- 大对象也会直接进入老生代。老生代当空间占用到达某个值之后就会触发全局垃圾收回，一般使用标记整理的执行算法。

## Serial 与 Parallel GC之间的区别？

- 相同的是，它们在GC的时候会引起stop-the-world
- 不同的是，serial 收集器是默认的复制收集器，执行GC的时候只有一个线程，而paraller收集器使用多个GC线程来执行。


## ZGC 垃圾收集器

- 一种低延迟垃圾收集器
- JDK 11中作为实验性特性引入
- 暂停时间（Pause Time）通常在毫秒级别，大堆内存时也能文档
- 基于Region的内存布局：ZGC将堆内存划分为多个大小相等的区域（Region），这些区域可以是小对象区域、大对象区域或者大数组区域。这种设计有助于提高内存使用的灵活性和效率。
- 并发标记-整理算法：ZGC使用并发标记-整理（Concurrent Mark-Compact）算法来进行垃圾回收，这意味着标记和整理阶段的大部分工作都是与应用线程并发执行的，从而减少了暂停时间。
- ZGC能够支持非常大的内存堆，理论上可以达到4TB

## 什么是JVM内存抖动，如何解决

JVM内存抖动是指JVM在进行垃圾回收时，由于对象的创建和销毁不平衡，导致内存的使用频繁地从新生代和老年代之间切换，从而导致系统的性能下降和响应时间延长的现象。

解决JVM内存抖动的方法包括：

1. 调整JVM的堆大小，增加新生代和老年代的比例，使得垃圾回收更加平衡。
2. 优化代码，减少对象的创建和销毁，避免频繁地进行垃圾回收。
3. 使用对象池技术，重复利用对象，减少对象的创建和销毁。
4. 使用GC日志分析工具，查看垃圾回收的情况，找出内存抖动的原因，进行优化。
5. 使用CMS垃圾回收器或G1垃圾回收器，这些垃圾回收器可以更好地处理内存抖动问题。

# JIT问题

## 为什么需要JIT

- JIT，也就是Java的即时编译。
- Java是一门半编译半解释的一门语言，Java代码编译成字节码，运行的时候字节码解释成机器码
- JVM跑久之后，热点代码的执行次数达到一定的阈值的时候，它会编译成更底层的机器码，节省了每次都要解释的时间，所以执行效率都会更高

## 为什么应用不启动的时候就把它编译成机器码呢

- 其实这样主要是为了考虑一个性能的开销
- 如果这样做的话，整个应用程序启动会非常的慢，文件大小也会变得更大
- 而代码也符合二八定律，也就是说20%的代码完成了80%的调用、
- 所以，动态的去识别热点代码，性价比会高一些

## JIT的分层编译

- 编译器有client、server两种
    - client 启动速度快，编译效率低。代表：c1编译器
    - server 启动速度慢，编译效率高。代表：c2编译器，graal编译器
- 分两层：代码先由client编译，随着代码变热，由server编译器重新编译。jdk8默认开启分层编译。
