HTTP

HTTP头部字段有哪些

  • Cache-Control 告诉所有的缓存机制是否可以缓存及哪种类型
  • Connection 表示是否需要持久连接
  • Content-Type 显示此HTTP请求提交的内容类型
  • Content-Encoding 服务器支持的返回内容压缩编码类型
  • Content-Length 响应体的长度
  • Set-Cookie 设置Http Cookie
  • User-Agent 浏览器类型
  • Accept 客户端能够接收的内容类型
  • Accept-Language 浏览器用来展示返回信息所优先选择的语言
  • Accept-Encoding 浏览器可以支持的web服务器返回内容压缩编码类型
  • Accept-Charset 浏览器可以接受的字符编码集
  • Referer 用户从该URL代表的页面出发访问当前请求的页面

HTTP 响应码有哪些？分别代表什么含义？

  • 200：请求成功
  • 301：永久重定向，可缓存，页面会保存新地址
  • 302：临时重定向，不可缓存，搜索引擎会抓取新网页的内容而保留旧的网址
  • 400：客户端请求错误，多为参数不合法导致 Web 服务器验参失败
  • 401：身份认证失败
  • 403：身份认证成功但是没有权限
  • 404：未找到资源
  • 500：Web 服务器错误，服务器处理客户端请求的时候发生错误
  • 503：服务器停机
  • 504：网关超时

HTTP和HTTPS的区别

  • 端口不同，HTTP是80端口，HTTPS是443端口
  • 安全性不同：HTTPS加密，比较安全
  • 消耗不同，HTTPS需要加密，所以消耗更高
  • HTTPS需要向CA申请证书

HTTPS的加密过程| SSL/TLS协议的加密过程

  • 客户端发起加密请求，也就是ClientHello 请求。
    • 发送的主要信息：
      • 客户端支撑的SSL/TLS版本
      • 客户端生产的随机数，用于生成会话密钥
      • 客户端支持的密码套件列表，如RSA算法
  • 服务器收到客户端请求后，向客户端发出响应，也就是 SeverHello。
    • 发送的主要信息：
      • 确认SSL/TLS协议
      • 服务端生产的随机数，用于生成会话密钥
      • 确认密码套件列表，如RSA算法
      • 服务端的证书
  • 客户端收到相应后，首先通过浏览器或者操作系统CA公钥确认证书的真实性。确认真实性后，用公钥加密报文
    • 发送的主要信息
      • 一个随机数，用于生成会话密钥
      • 加密通信算法改变通知
      • 客户端握手结束通知
  • 服务端收到第三个随机数后，通过加密算法，生成本次会话密钥，然后向客户端发送信息
    • 发送的主要信息：
      • 加密算法改变的通知
      • 服务端握手结束

HTTP1.0、1.1、2.0有什么区别

  • 1.0采用短链接，每次请求都建立一次链接
  • 1.1采用长链接，链接可以重复使用
  • 2.0 引入数据帧和流的概念，采用多路复用机制，支持并行传输

如何理解HTTP无状态

  • 无状态，指的是服务器不知道客户端是什么状态，比如，两个请求，仅仅通过HTTP协议，服务端无法知道是不是同一个用户发的请求

什么是HTTP长链接和短链接

  • HTTP的长链接和短链接，本质就是TCP的长链接和短链接
  • HTTP1.0默认就是短链接，链接在任务结束的时候就中断了
  • HTTP1.1默认的是长链接，长链接情况下，任务结束不会中断，下一次继续访问服务器的时候后重用当前链接。

说说长连接，短连接的操作过程

  • 短链接：建立链接-数据传输-关闭链接
  • 长链接：建立链接-数据传输-（保持链接）-数据传输-关闭链接

HTTP和RPC的区别

  • RPC 远程过程调用 ，是一种概念，核心概念是：调用远程方法像调用本地方法一样
  • HTTP 是一种具体的协议，可以作为远程过程调用的协议，HTTP Restful 常作为RPC的一种实现
  • 区别
    • 传输协议
      • RPC可以使用http，也可以使用更底层的tcp
      • HTTP基于HTTP协议
    • 传输效率
      • RPC因为可以使用自定义的TCP协议，可以让报文更小，可以提高传输效率
      • HTTP 如果是HTTP1.1，那么请求体会有很多无用的报文。如果是HTTP2.0的话，稍微有点好转。
    • 性能消耗
      • RPC可以使用thrift协议实现高效的二进制传输
      • HTTP大部分都是通过json实现的，从消耗上看肯定比二进制高

Get 和 Post 请求有哪些区别？

  • 用途不同：get一般是从服务器获取资源，post是向服务器创建资源或提交数据
  • 表单提交方式：get会把表单的数据以key1=value1&key2=value2的形式拼接到URL上。post的数据会放到请求头或者请求消息体中。
  • 数据传输大小不同：get请求传输数据受到URL长度限制（2048个字符），而URL长度限制是浏览器决定的。post请求理论上没有限制。
  • 参数编码：get请求一般是以明文的方式拼接到URL上。而post请求则以二进制等多种编码形式提交数据。
  • 浏览器缓存：get能被收藏和缓存，post不能被收藏和缓存。
  • 关于get请求发送一个tcp，post发送两个tcp的讨论：https://github.com/amandakelake/blog/issues/20

TCP

TCP和UDP的区别

  • TCP面向连接，传输可靠，但效率低
  • UDP无需连接，效率高，但传输不可靠
  • TCP连接是点对点的，UDP支持一对一，一对多，多对多

TCP三次握手

  • 客户端随机初始化一个客户端号码client_isn，作为SYN报文的内容发送给服务端，该报文不包含应用层数据，此时，客户端处于SYN_SEND状态
  • 服务端接受到SYN报文，把客户端号码+1作为新的SYN报文，同时服务端随机生成一个服务端号码server_isn，作为ACK的内容，接着把SYN和ACK一起发送给客户端，该报文不包含应用层数据。此时服务端处于SYN_RECE状态
  • 客户端收到消息后，把ACK的服务端号码+1，作为应答把ACK报文发送给服务端，这次报文可以携带客户到服务器的数据。此时客户端，处于ESTABLISHED 状态
  • 服务器收到客户端的应答报文后，也进入 ESTABLISHED 状态。

TCP为啥要三次握手，两次不行吗

  • TCP是可靠的协议，为了满足可靠性，三次连接是理论上最小的连接次数
  • 从三次握手的过程看，如果不要第二次连接，那么服务端无法知道服务端是否接收到我的报文，无法确认第一次连接的连通性

TCP四次挥手

  • 客户端打算关闭连接，此时会发送一个 TCP 首部 FIN 标志位被置为 1 的报文，也即 FIN 报文，之后客户端进入 FIN_WAIT_1 状态。
  • 服务端收到该报文后，就向客户端发送 ACK 应答报文，接着服务端进入 CLOSED_WAIT 状态。
  • 客户端收到服务端的 ACK 应答报文后，之后进入 FIN_WAIT_2 状态。
  • 等待服务端处理完数据后，也向客户端发送 FIN 报文，之后服务端进入 LAST_ACK 状态。
  • 客户端收到服务端的 FIN 报文后，回一个 ACK 应答报文，之后进入 TIME_WAIT 状态
  • 服务器收到了 ACK 应答报文后，就进入了 CLOSED 状态，至此服务端已经完成连接的关闭。
  • 客户端在经过 2MSL 一段时间后，自动进入 CLOSED 状态，至此客户端也完成连接的关闭。

TCP的队头阻塞问题

TCP（传输控制协议）的队头阻塞（Head-of-Line Blocking, HOLB）问题是指在网络通信过程中，由于TCP的按序传输特性导致的数据包处理效率问题。具体来说，当TCP连接中的某个数据包丢失或出错时，TCP协议要求后续的所有数据包都必须等待这个数据包被重新传输并正确接收后，才能被处理。即使这些后续数据包已经到达目的地，它们也必须排队等待，这就形成了队头阻塞。 队头阻塞的影响主要体现在以下几个方面：

  1. 延迟增加：当发生队头阻塞时，即使后续的数据包已经到达，也不能立即处理，这会导致通信延迟增加。
  2. 吞吐量下降：由于队头阻塞，网络的吞吐量会受到影响，因为后续的数据包不能被及时处理。
  3. 资源浪费：等待重传的数据包占用了网络资源，而这些资源在数据包被正确传输之前无法被其他通信使用。 为了缓解TCP队头阻塞问题，研究者们提出了多种改进方案，如：
  • 选择性确认（Selective Acknowledgment, SACK）：允许接收方明确告知发送方哪些数据已经被成功接收，哪些需要重传，从而减少不必要的重传。
  • 多路径TCP（Multipath TCP）：通过同时在多个网络路径上传输数据，当一条路径上的数据包遇到队头阻塞时，其他路径上的数据包可以继续传输，提高了网络的鲁棒性和效率。
  • 丢包检测和快速重传：改进的TCP版本能够更快地检测到丢包，并触发快速重传机制，减少等待时间。 这些改进措施在一定程度上缓解了TCP队头阻塞问题，提高了TCP的性能。然而，在某些特定场景下，如实时通信应用，队头阻塞问题仍然是一个需要考虑的重要问题。

TCP粘包产生原因，如何解决

TCP粘包问题是指在使用TCP协议传输数据时，发送方发送的多个数据包在接收方可能会被当作一个数据包处理，或者一个数据包中的数据可能会被拆分成多个数据包接收。这种现象的原因和解决方法如下：

产生原因

  1. TCP的数据传输特性：TCP是一种面向流的协议，它以字节流的形式传输数据，没有固定的消息边界。因此，当发送方连续发送多个数据包时，接收方可能会一次性接收到这些数据包，导致粘包现象。
  2. TCP的Nagle算法：为了提高网络效率，TCP实现了一个称为Nagle算法的机制，它会在发送方小数据包的情况下进行缓冲，等到有更多的数据或者收到上一个数据包的确认时才发送。这可能导致多个小数据包被合并成一个大数据包发送。
  3. MTU（最大传输单元）限制：当数据包的大小超过网络层的MTU时，数据包会被拆分。如果这些拆分的数据包在不同的网络条件下到达接收方，可能会出现粘包或拆包现象。

解决方法

  1. 消息定长：发送固定长度的消息，这样接收方每次读取固定长度的数据即可。这种方法简单，但可能不适用于所有场景，因为不是所有消息都能被固定长度限制。
  2. 消息边界：在消息之间添加特殊的分隔符或者标志，接收方通过这些分隔符来区分不同的消息。这种方法灵活，但需要处理分隔符与消息内容冲突的问题。
  3. 长度字段：在消息头部添加一个表示消息长度的字段，接收方首先读取这个长度字段，然后根据长度读取相应长度的消息内容。这种方法较为通用，但需要额外处理长度字段。
  4. 框架或协议：使用现有的网络通信框架（如Netty、gRPC等）或自定义通信协议，这些框架或协议通常内置了解决粘包问题的机制。
  5. 关闭Nagle算法：在某些场景下，可以通过设置TCP套接字的TCP_NODELAY选项来关闭Nagle算法，使得每个小数据包都能立即发送，减少粘包的可能性。 通过上述方法，可以在不同程度上解决TCP粘包问题，提高数据传输的准确性和效率。

七层模型和五层模型

OIS七层模型

物理层（Physical Layer） 数据链路层（Data Link Layer） 网络层（Network Layer） 传输层（Transport Layer） 会话层（Session Layer） 表示层（Presentation Layer） 应用层（Application Layer）

TCP位于传输层，它负责在网络中的两个端点之间提供可靠的、面向连接的数据传输服务。

应用层有哪些协议：

应用层是OSI模型的最高层，它直接为用户的应用程序提供服务。应用层协议包括但不限于以下几种：

  • HTTP（超文本传输协议）：用于Web浏览器和服务器之间的通信。
  • HTTPS（安全超文本传输协议）：HTTP的安全版本，通过SSL/TLS加密数据传输。
  • FTP（文件传输协议）：用于文件的上传和下载。
  • SMTP（简单邮件传输协议）：用于电子邮件的发送。
  • POP3（邮局协议版本3）：用于电子邮件的接收。
  • IMAP（互联网消息访问协议）：另一种用于电子邮件接收的协议，相比POP3提供更多功能。
  • DNS（域名系统）：将域名解析为IP地址。
  • SSH（安全外壳协议）：用于安全地访问远程计算机。
  • Telnet（远程终端协议）：用于远程控制计算机。
  • SNMP（简单网络管理协议）：用于网络设备的管理。
  • XMPP（可扩展消息与存在协议）：用于即时消息（IM）和在线状态信息。
  • RTP（实时传输协议）：用于音频和视频的实时数据传输。 这些协议定义了不同应用程序如何在网络上进行通信，以及如何交换数据。

五层模型

五层模型是对OSI七层模型的一种简化，它将网络通信的过程分为五个不同的层次，合并了OSI模型中的一些层次。五层模型通常包括以下层次：

  1. 物理层（Physical Layer）：负责传输原始比特流，即电信号的传输，包括电缆、光纤、无线电波等。
  2. 数据链路层（Data Link Layer）：负责在相邻节点之间的可靠链接，包括帧的封装/解封装、差错检测与纠正等。
  3. 网络层（Network Layer）：负责数据包从源到目的地的传输和路由选择，包括IP地址的分配和路由协议等。
  4. 传输层（Transport Layer）：负责提供端到端的数据传输服务，确保数据的正确性和有效性，包括TCP和UDP协议。
  5. 应用层（Application Layer）：为用户的应用程序提供服务，包括HTTP、FTP、SMTP、DNS等协议。 五层模型简化了OSI模型的复杂性，将会话层和表示层合并到应用层中，将物理层和数据链路层合并为单一的物理层。这种简化有助于理解和教授网络通信的基本原理，而且在实际应用中，会话层和表示层的功能通常被应用层协议自身所包含或处理，因此五层模型在实际网络通信中更为常见。

浏览器

输入url到浏览器，enter后会发生什么

  • 检查资源是否存在缓存，有缓存就直接返回，没缓存就去服务器拿
  • 解析域名为IP地址。DNS查询，DNS解析顺序：浏览器、host文件、路由、dns服务器
  • 根据IP向服务器发送请求，返回响应
  • 浏览器接收响应后，渲染页面

session和cookie的区别

  • Session和Cookie都是HTTP无状态的产物。
  • 每一次会话请求，服务端都会生成sessionId保存到服务器端，同时把sessionId返回给客户端，以cookie的形式保留下来。每次向服务端发送请求的时候都会带上cookie，服务端通过解析cookie得到session来验证是否是同一个用户。
  • 他们的区别是：
    • session在服务端生成，作为一种文件或者数据库保存到服务端。而cookie保存到客户端。
    • session一般都是依赖于Cookie的，如果cookie被禁用，session一般也会生效。

浏览器禁用cookie，session怎么办

  • 重写URL的形式，每次请求把sessionId拼接到url上

Cookie 和 Session 的区别

  • Cookie
    • Cookie是浏览器用来保存服务端数据的一种机制。
    • 服务器可以把数据以 key-value的方式写入到 Cookie 里面存储到浏览器。
    • 然后浏览器下一次再访问服务器的时候，可以携带这些数据，服务端可以根据 Cookie 里面携带的内容来鉴别身份。
  • Session
    • 默认情况下，每一个浏览器的请求。Servlet 容器都会分配一个 Session。
    • 我们都知道， Http 协议本身是一个无状态协议，也就是服务器并不知道客户端发送过来的多次请求是属于同一个用户。
    • 所以 Session 是用来弥补 Http 无状态的不足，简单来说，服务器端可以利用session 来存储客户端在同一个会话里面的多次请求记录。
    • 基于服务端的 session 存储机制，再结合客户端的 Cookie 机制，就可以实现有状态的 Http 协议。
  • 总的来看， Cookie 是客户端的存储机制， Session 是服务端的存储机制。

Forward（转发） 和 Redirect（重定向） 的区别？

  • 首先呢，转发是我们向服务器发送请求，服务器向另一个服务器请求后处理完返回给客户端。而重定向，是我们向服务器发送请求，服务器告诉我们另一个服务器的地址，需要客户端再次请求一下另一个服务器。
  • 区别：
    • forward浏览器URL不会变，redirect浏览器的URL会变。
    • 请求次数，Forward只请求一次，Redirect请求2次
    • 因为转发是同一个请求，所以request 的数据是共享的。而redirect（转发）是分别两个请求，所以request的数据是不共享的。
